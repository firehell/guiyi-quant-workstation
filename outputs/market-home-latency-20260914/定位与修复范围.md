# 首页慢请求与品种目录依赖：只读定位

状态：COMPLETED（诊断完成，产品修复未实施）。检查日期：2026-09-14。

结论：首页缺少可命中的预计算投影，进入 60 品种 D1/W1 现场计算；W1 路径对同一周交易日历反复访问数据库，是已验证的主要热点。首页搜索和消息品种选项又依赖该慢请求返回的行情行，放大为目录不可用。精确修复范围为请求内日历复用、目录独立读取、行情资源到期/失败后的有界恢复。

- 独立诊断进程使用实际 Runtime 模块和真实数据，数据库事务为只读；对照实验额外使用 repeatable read，结束 rollback。没有生产代码、配置、投影、Canonical 或业务数据库写入。

## 后端调用链与因果验证

`GET /market/research/home-overview → build_market_home_projection(...).read() → identity + store.load → 未命中 → MarketHomeOverviewService.snapshot → 60 × (D1 limit 300 + W1 limit 80)`。

主要位置：

- `services/quant-api/app/market_data/market_home_projection.py:233`：只读回退；HTTP 不发布投影。
- `services/quant-api/app/market_data/market_home_overview.py:148`：逐品种现场读取 D1/W1。
- `services/quant-api/app/market_data/market_data_service.py:686`、`:789`、`:841`：候选周线过滤和分页边界校验均调用 `_page_weekly_owner`；后者每次重新查询所属 ISO 周日历。
- `services/quant-api/app/market_data/catalog.py:404`、`:416`：每次日历查询先查品种交易所，再查交易日历，形成两次 SQL。

一次完整读取调用 `trading_days` 28,000 次，但 `(symbol, start, end)` 只有 4,970 个不同组合，重复 23,030 次，同一组合最多出现 11 次。cProfile 中日历调用累计 21.650 秒；该值与调用它的父函数累计耗时重叠，不应相加。分区读取 3,385 次、累计约 4.55 秒，为后续可观察的次级成本。

在同一 repeatable-read/read-only 事务中，仅在诊断进程复用完全相同的日历查询结果：

| 模式 | 完整读取耗时 | SQL 次数 | 返回品种 |
|---|---:|---:|---:|
| 原实现 | 21.251 秒 | 56,962 | 60 |
| 相同日历键在本次读取内复用 | 7.394 秒 | 10,902 | 60 |

减少 46,060 次 SQL（80.9%），墙钟耗时下降 65.2%。两次完整响应 SHA-256 均为 `3eaba246ac96f1e79831d67c0dd3b7cd31ed909f2bd0e887dba6e400ae0a2c73`。SQL 减少量恰好等于重复日历查询数的两倍。此对照支持因果定位；单次顺序实验的耗时仍可能受缓存和系统负载影响，也不能替代异常输入、跨请求更新和完整分页回归。

`profile.json` 的 57,265 次 SQL 还包含额外 preflight 身份读取；对照表中的 56,962 次才是该实验单次完整读取的统计范围，二者不能混用。

当前 `<canonical_root>/.derived/market-home-overview.json` 不存在，自然盘后投影开关为关闭。关闭状态符合默认合同，不能据此判定配置错误。启用或首次生成生产投影属于单独操作范围，本轮没有执行。

## 目录依赖与恢复问题

当前依赖为：`overview.items → marketHomeViewModel.rows → index.vue → Header 搜索选项 + Messages 品种筛选/名称`。

- `MarketHomeHeader.vue` 与 `MarketHomeMessages.vue` 都从行情 rows 构造品种选项；没有自己的目录资源。因此行情慢、首载失败或有效 degraded 响应中行情行被排除时，目录也受影响。
- 后端会按合同排除没有目标交易日 D1 的品种；不能用伪行情补齐行数来修复目录。有效的零行响应也不等于目录读取失败，当前 Header 按 rows 数量推导目录状态会混淆两者。
- 详情页 `useMarketDetailController.ts` 独立读取现有 `/market/dominants`，所以首页目录为空时详情仍可能正常选择黄金、焦煤。该接口本次 0.329 秒返回 60 品种。
- Live 投影使用 `rows.map(...)` 更新已有行，无法恢复缺失的基础行。WebSocket 连通不代表首页全量快照已恢复。
- `useMarketHome.ts:74` 的 60 秒定时器只刷新 Runtime。overview 的五分钟 TTL 仅在挂载/恢复可见等触发时检查；持续停留可见页面，TTL 到期本身不会触发重读。请求失败后也没有该定时器驱动的恢复。这是代码确认的恢复缺口，不是已证明的原 49.857 秒成因。
- overview 的缓存是模块内内存，不能解决硬刷新首载；有效 degraded 响应是成功响应，可能替换旧数据。不得把它一概当作网络失败或静默保留旧快照冒充最新。

约束：`openspec/specs/market-home-overview/spec.md:184` 当前明确禁止浏览器调用 product dominants。目录独立读取必须同步修改该条权威资源合同及 E2E 请求白名单，明确允许一个现有批量目录请求，继续禁止每品种扇出请求和写请求。

## 精确修复范围

| 范围 | 最小改动位置 | 验收重点 |
|---|---|---|
| A. W1 日历重复读取 | `market_data_service.py` 内同一次 page 读取的上下文；必要时调整 `catalog.py` 的窄接口 | 候选筛选与边界校验复用相同日历事实；当前 60 品种响应逐值一致；同周 SQL 不随逐日/逐 Bar 调用重复增长 |
| B. 品种目录独立 | 一个共享首页目录资源；`index.vue`、`MarketHomeHeader.vue`、`MarketHomeMessages.vue`；对应 spec / E2E 白名单 | 使用已有 bulk dominants 和既有规范化口径；独立 loading/error；overview 慢、失败、零行时 AU/JM 仍可搜索和消息筛选；只产生一次并发合并后的目录请求 |
| C. 有界自动恢复 | `useMarketHome.ts` 既有定时器/资源逻辑 | 可见时检查过期/失败资源；有效五分钟缓存不重复全量读取；保留 in-flight 合并、generation 防旧响应、隐藏页停止和失败状态；不形成无界重试或高频轮询 |

A 应限定在单次读取生命周期，避免长期或跨请求缓存导致同日交易日历/品种元数据更新不可见。不得复用不同请求身份、不同查询区间的结果，也不得改变 strict mapping、缺失日历报错、completed week、主力归属、分区完整性和游标语义。

本次范围不包含：提高 30 秒超时来掩盖成本、并发启动 60 份数据库读取、新增数据源、下载/补齐 AU/JM 历史、调整公式/收益、创建全局日历缓存、重构整个详情页、启用生产投影、修复此前其他巡检项。现有投影命中小于 200 毫秒的目标与 fallback 优化是不同验收项；7.394 秒实验结果不证明前者。

建议实现后的性能验收：相同 60 品种和明确投影命中状态下，分别记录 HTTP、D1/W1、SQL 数及冷/热读取；以 fallback 低于 10 秒作为此次实测支持的初始目标，仍须正式实现后验证。目录不得等待 overview 的 30 秒超时。保留原数据缺失分母和错误，不通过缩小读取范围达成性能指标。
