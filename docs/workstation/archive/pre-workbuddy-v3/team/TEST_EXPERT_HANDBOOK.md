# 归一量化测试专家工作手册

生成时间：2026-07-09
版本：v1.0
作者视角：测试专家 / QA Lead（见 `ROLE_SPEC.md` 第 8 角色）
配套文档：`ROLE_SPEC.md`、`TASK_MATRIX.md`（测试体系建设任务类型）、`STATE_MACHINE_TICKET.md`（TESTING / FAILED 状态）、`DAILY_COMMANDS.md`（命令 6 测试计划 / 命令 14 失败复盘）
项目硬约束（所有测试不得违背）：V1 不自动交易；分钟数据以 1m 为基础，其他周期系统内聚合；RQData 为主数据源；主机 Mac mini；XMA 原始信号不进正式信号；Stage 9 企业微信只读提醒默认 dry-run、preview≠sent、真实发送需显式授权。

## 0. 测试专家定位与红线

### 0.1 职责边界

测试专家在「涉及代码开发」的任务中**必须参与**（见 `TASK_MATRIX` 强制规则）。负责：制定测试策略、定义单元/集成/回归/烟测/长稳/数据一致性/告警测试、检查数据聚合正确性、检查策略信号触发准确性、检查企业微信告警重复/漏发/误发、检查 Mac mini 长期运行稳定性、输出测试用例与验收结论。

### 0.2 测试红线（无条件生效）

- ❌ 不自动下单、不生成订单草稿（V1 边界）。
- ❌ 不读取或打印 `QYWX_WEBHOOK_URL`、token、密钥；真实发送测试需你显式授权且仅走 CLI `--run-send --confirm-observation-only`。
- ❌ 不删除数据库记录、parquet、日志（与全局护栏一致）。
- ❌ 不自动 push / merge / deploy；测试结论只供你决策。
- ⚠️ preview / dry-run 测试**不得**写 `SignalNotification`、不得真实发送；断言 `would_send=false`。
- ⚠️ 验收测试只能基于 `quality_status != failed`、`data_role=primary`、`provider ∈ {rqdata, local_parquet}` 的 active 数据（active Gate）。

## 1. 测试分层

| 分层 | 目标 | 范围 | 方法/工具 | 触发时机 | 通过标准 |
|---|---|---|---|---|---|
| **单元测试** | 单函数/单模块逻辑正确 | 聚合函数、Gate、重绘检测、格式化、幂等键生成 | pytest（仓库 `services/quant-api/tests/`） | 每次开发完成 | 覆盖率达标，边界用例全绿 |
| **集成测试** | 跨模块协作正确 | 数据写入→读取、信号→事件→Gate→payload、API→DB | pytest + 测试 DB + fixtures | CODING 完成、TESTING 起 | 端到端链路无断点 |
| **回归测试** | 改动不破坏既有能力 | 全部历史关键用例 + 已知 bug 守护用例 | pytest 全量 + CI | 每次 PR / 合并前 | 全量绿，无已知 bug 复现 |
| **烟测 (smoke)** | 最小可用不被破坏 | `/health`、`/api/health`、`/healthz`、关键 API 冒烟 | curl / API 调用 | 部署后、长稳前 | 关键端点 200，核心读链通 |
| **长稳测试** | 长期运行稳定 | 断网/重启/日志增长/进程崩溃/数据源失效/定时恢复 | Mac mini 上常驻 + 监控脚本 | APPROVED_DEV 后择机 | 连续 N 天无僵死、无泄露 |
| **数据一致性测试** | 数据不丢不错不重 | 1m 完整性、聚合对齐、夜盘跨日、交易日边界、缺失/重复 bar、合约切换、RQData 异常 | 校验脚本 + DB 比对 | 数据模块改动必跑 | 计数/边界/checksum 一致 |
| **告警测试** | 提醒正确不扰民 | 重复发送、漏发、格式、风险提示、webhook 重试、网络异常 | dry-run + 授权真实 smoke + mock webhook | 企业微信相关改动必跑 | 幂等、格式合规、重试可控 |

> 分层与状态机对应关系：单元测试/集成/数据一致性/告警测试 → `TESTING`；烟测/长稳 → `DELIVERY_READY` 前与之后常驻；回归 → `CLOSED` 前（命令 15 合并前检查）。

## 2. 数据测试重点

### 2.1 1m bar 完整性
- **方法**：对目标品种/交易日，校验 1m bar 数量 = 预期交易分钟数（日盘 + 夜盘，考虑午休跳过）；统计缺失分钟偏移。
- **预期**：无整段缺失；单根 bar 的 `datetime` 连续、不重叠、`volume≥0`。
- **判定**：缺失分钟数 > 阈值即失败（夜盘与日盘分段计）。

### 2.2 1m → 多周期聚合
- **覆盖周期**：`1m → 5m / 15m / 30m / 1h / 日线 / 周线`。
- **方法**：用已知 1m 序列手算聚合值，与系统输出逐字段比对（`open=首根open`、`close=末根close`、`high=max`、`low=min`、`volume=sum`）。
- **预期**：聚合对齐到周期边界（如 5m 以 `HH:00/05/...` 对齐）；最后一根不完整周期不误判为完整。
- **判定**：任意周期 open/high/low/close/volume 偏差 > 1e-6 即失败；不完整周期标记正确。

### 2.3 夜盘跨日
- **方法**：构造夜盘 `21:00–23:00`（当日）与 `00:00–02:30`（次日）连续品种，校验跨日拼接是否连续、交易日归属是否正确（按交易所规则归属到开盘日）。
- **预期**：跨日 bar 不重复、不丢失；交易日标签符合期货日历。
- **判定**：跨日出现断点/重复/归属错即失败。

### 2.4 交易日边界
- **方法**：在节假日、周末、合约最后交易日前后构造数据，校验边界裁剪。
- **预期**：非交易日无 bar；最后交易日后无新 bar（除非展期）。
- **判定**：边界外出现 bar 或边界内缺失即失败。

### 2.5 缺失 bar
- **方法**：注入随机缺失分钟，校验系统检测与告警/补数逻辑；确认不影响聚合崩溃。
- **预期**：缺失被记录（`quality_status` 标记），聚合跳过或插值策略明确。
- **判定**：缺失导致聚合异常退出即失败。

### 2.6 重复 bar
- **方法**：注入同 `datetime` 重复 bar，校验去重/覆盖策略。
- **预期**：重复 bar 被去重（保留其一），不导致 volume 翻倍。
- **判定**：出现 volume 翻倍或重复记录即失败。

### 2.7 合约切换（主力切换）
- **方法**：在主力换月日构造 `continuous_contract` 与 `actual_contract` 映射变化，校验 `actual_contract` 不为 `*.MAIN`、映射日期非空。
- **预期**：真实合约映射正确，`dominant_mapping_date` 写入；切换日前后信号归属正确。
- **判定**：`actual_contract=*.MAIN` 进入正式信号即失败（Stage 9 Gate 必拦）。

### 2.8 RQData 异常
- **方法**：mock RQData 限流/超时/空响应/字段缺失，校验降级与重试、不污染 active 数据。
- **预期**：异常被捕获；失败数据 `quality_status=failed` 不进入 active；有可观测日志（无密钥泄露）。
- **判定**：异常数据进入 active 读链即失败。

## 3. 策略测试重点

### 3.1 信号只在确认收盘后触发
- **方法**：在 bar 未收盘时喂入数据，断言不生成 `signal_created`/`signal_changed`；收盘确认后触发。
- **预期**：无"未来"信号；`bar_end` 非空且为 confirmed bar。
- **判定**：未收盘即触发即失败。

### 3.2 是否重复触发
- **方法**：同一确认 bar 重复喂入，断言同 `dedupe_key` 只产生一条事件（参考 `signal_created:{dedupe_key}` 去重口径）。
- **预期**：`signal_events` append-only 但事件不重复；企业微信侧幂等键 `enterprise_wechat:signal_event:{event.id}` 防重。
- **判定**：同信号重复落库/重复发送即失败。

### 3.3 是否漏触发
- **方法**：用已知应触发的标注样本回放，统计召回率；重点覆盖边界参数。
- **预期**：标注样本召回 ≥ 约定阈值。
- **判定**：明确应触发却未触发即失败（记录漏触发样本）。

### 3.4 是否重绘（未来函数）
- **方法**：对指标在 bar 进行中 vs 收盘后分别计算，比对信号是否变化；**专项核查 XMA 类指标**。
- **预期**：信号不随后续数据回溯改变；原始 XMA / XMA 派生信号**不得**写入 `signal_events`（XMA PoC 风险结论）。
- **判定**：出现重绘或 XMA 进正式信号即失败。

### 3.5 参数边界
- **方法**：对策略参数取边界值/极端值（0、极大值、负值、空池），校验不崩溃、不误触发。
- **预期**：边界下行为确定、可解释。
- **判定**：边界导致异常退出或静默错误即失败。

### 3.6 多周期信号一致性
- **方法**：同一策略在 15m/5m 等周期分别运行，校验跨周期信号逻辑不自相矛盾（如方向冲突）。
- **预期**：多周期结论可解释一致；`continuous_contract`/`actual_contract` 上下文一致。
- **判定**：同标的跨周期出现无法解释的方向冲突即失败。

### 3.7 V1 不自动交易守护（跨策略强制）
- **方法**：在任意策略/信号测试断言产物中检查不含订单草稿、`auto_order=false`、`trading_instruction=not_trading_instruction`。
- **判定**：出现任何下单/交易指令即失败（最高优先级）。

## 4. 企业微信告警测试

> 端点：`GET /api/signals/events/{event_id}/stage9-wechat/preview`（只读，不发送）、`GET /api/signals/events/{event_id}/stage9-wechat/notification`（只读查状态）。CLI：`scripts/stage9_wechat_send_once.py`、`scripts/stage9_jm_v1b_replay_event_once.py`，默认 dry-run。

### 4.1 是否重复发送
- **方法**：对同一 `event_id` 连续调用发送 CLI / 模拟 retry，校验幂等键。
- **预期**：`enterprise_wechat:signal_event:{event.id}` 保证同一事件只发送一次；`attempt_count` 正确递增但只成功发送一条。
- **判定**：同一事件产生多条 `sent` 通知即失败。

### 4.2 是否漏发
- **方法**：构造一批 Gate 通过的 eligible 事件，校验全部进入发送队列并落 `SignalNotification`。
- **预期**：Gate 通过且未被 skip 的事件均有对应通知记录（`sent`/`retry_pending`/`failed`）。
- **判定**：Gate 通过却无任何通知记录即失败。

### 4.3 格式是否正确
- **方法**：解析 markdown payload，校验必含字段：`actual_contract`、`continuous_contract`、`bar_end`、`trigger_price`、`quality_status`、`provider/source`。
- **预期**：格式合规、可读；`notice_scope=observation_only`、`trading_instruction=not_trading_instruction`、`auto_order=false` 明确表达。
- **判定**：缺必含字段或表达歧义即失败。

### 4.4 是否包含风险提示
- **方法**：断言 payload 含风险提示语（"仅供观察，不构成交易建议"类）与 `observation_only` 标识。
- **判定**：缺风险提示即失败。

### 4.5 webhook 失败重试策略
- **方法**：mock webhook 返回 5xx/超时，校验 `status=retry_pending` → 最多 `max_attempts=3` 次重试 → `failed`；`next_retry_at` 合理。
- **预期**：重试可控；达到上限标记 `failed`；不无限重试。
- **判定**：重试次数超限或不足即失败。

### 4.6 网络异常处理
- **方法**：断网/超时场景，校验不崩溃、记录 `last_error_type`、preview 不受影响（`would_send=false`）。
- **预期**：异常可观测；preview/dry-run 不读 webhook、不写通知。
- **判定**：网络异常导致进程崩溃或误发即失败。

### 4.7 敏感字段脱敏（专项）
- **方法**：扫描 payload 与日志，确认过滤 `webhook`/`token`/`password`/`cookie`/`secret`；`QYWX_WEBHOOK_URL` 不出现。
- **判定**：出现任何密钥即失败（安全专家一票否决联动）。

## 5. Mac mini 长期运行测试

> 主机 Mac mini；常驻方式见 DevOps 方案（tmux/launchd/daemon/supervisor）；日志轮转与状态检查见 `ALIYUN_WEB_HOSTING_PLAN.md` / DevOps 评审。

### 5.1 断网
- **方法**：拔网/关 Wi-Fi，观察数据监听与发送降级。
- **预期**：进程存活，本地缓存/待重连；恢复后补数据或安全跳过；不崩溃、不重复发历史。
- **判定**：断网导致崩溃或恢复后重复发送即失败。

### 5.2 重启
- **方法**：`launchd`/`tmux` 重启主机或进程，校验自启与状态恢复。
- **预期**：开机自启；断点续跑；不重复发送未确认事件。
- **判定**：重启后无法自启或重复发送即失败。

### 5.3 日志增长
- **方法**：常驻运行观察日志体积，校验轮转生效。
- **预期**：日志按策略轮转，磁盘不溢出；敏感字段不落日志。
- **判定**：日志无限增长或无轮转即失败。

### 5.4 进程崩溃
- **方法**：kill 主进程，校验守护/重启与告警；core/异常可观测。
- **预期**：被守护重启或上报；不静默丢失信号。
- **判定**：崩溃无重启无告警即失败。

### 5.5 数据源失效
- **方法**：RQData 不可用，校验降级与 `quality_status=failed`、不污染 active、有告警。
- **预期**：失败数据不进 active；人工可感知。
- **判定**：失效数据进 active 或无告警即失败。

### 5.6 定时任务恢复
- **方法**：停止 scheduler 后恢复，校验错过的定时任务补跑/跳过策略正确。
- **预期**：恢复后状态一致，不重复执行已完成的定时任务。
- **判定**：定时任务重复执行或永久丢失即失败。

## 8. 测试失败处理流程

> 对应状态机 `FAILED → REPLAN → PLAN_READY` 与命令 14（测试失败复盘）。

```text
测试失败
  ↓
1. 分类根因：数据 / 逻辑 / 环境 / 边界 / 外部依赖
2. 影响范围评估：是否污染 active 数据、是否误发告警、是否触及 V1 红线
3. 紧急止损（如需）：停相关常驻进程 / 暂停发送 / 回滚到上一已知好状态
4. 输出《失败复盘报告》（命令 14）：
   - 根因 + 复现步骤
   - 影响范围
   - 修复建议（给出 REPLAN 方向）
   - 回归测试清单（防止复发）
   - 验收标准（修复后）
   - 风险点
5. 状态流转：FAILED →（你确认）→ REPLAN → PLAN_READY
6. 修复后重新走：单元测试 → 集成 → 数据一致性/策略/告警 → 回归 → 长稳（按需）
7. 红线相关失败（自动交易/误发/密钥泄露）：立即升级，安全专家一票否决，不自动恢复
```

**失败分级**：
- **P0（红线级）**：自动交易、误真实发送、密钥泄露、active 数据污染 → 立即止损 + 安全专家介入。
- **P1（功能级）**：信号漏/重触发、聚合错、Gate 失效 → 退回 REPLAN。
- **P2（稳定级）**：长稳/日志/重试策略瑕疵 → 排期修复，不阻塞合并（标风险）。
