### 已由代码和回执证明

1. `_execute_apply` 按 fetch group 获取、验证和提交；后续 group 失败时，同合约较早 group 已提交。
   P7 的 24 个冲突均为 partial，说明逐月小批执行无法避免同合约部分更新。
2. `_require_contract_weekly_daily_parity` 只在包含待处理 W1 的当前 group 上校验。
   仅更新 D1、受影响但没有被选入目标的旧 W1，需要额外的依赖闭包检查。
3. `_commit_partition` 是单分区 Catalog 提交；整个 D1/W1 组目前没有原子可见性合同。
4. 普通 warm-up 主要补缺失端点；存在数值冲突但端点齐全的旧 W1，可能没有可执行修复目标。
5. 单分区维护读回与最终 Newow 周线质量读回不等价。EC、RB、RU 的真实结果证明存在验收覆盖差距。
6. 119 个 REVIEW_REQUIRED 单元不能由普通补数计划处理；来源非正价格需要质量事实分类。

### 尚待逐样本证明

不能把全部 WEEKLY_SOURCE_BAR_CONFLICT 归因为 RQData 历史修订。本轮曾观察到 turnover 差异，
但错误码还包含缺日、重复日、周末端点与整条 Bar 不相等。必须区分：来源值变化、解析/聚合精度、
旧 W1 生成口径、跨月刷新顺序、日历/生命周期，以及当前守卫本身的缺陷。
Canonical 当前以 decimal128(38,18) 存储，适配器使用 Decimal(str(value))，不能仅凭微小差异断言
“Parquet float 误差”；也不能因为价格未变就忽略 turnover 或把比较改为任意 epsilon。

## 3. 方案选择

| 方案 | 收益 | 问题 | 结论 |
| --- | --- | --- | --- |
| 沿用旧队列继续补数 | 改动少 | 已知会重复产生 partial，不能修复端点齐全的冲突 | 不采用 |

| 按受影响依赖范围核对、版本化修复、小样本验证后逐品种恢复 | 保留有效事实，修复共性链路，范围可审计 | 需要增强 planner、发布和读回 | 推荐 |

不新建恢复平台、第二套行情入口或手工缺口数据库。复用 HistoricalDataManager、现有恢复脚本、
CanonicalMonthlyStore、MarketCatalog、weekly_quality、MDS 和 NewowProductReader。

## 4. 期货与数值合同

- 单位必须包含 symbol、physical_contract、frequency、完整端点集合和生命周期；不把不同交割月价格拼成一周。
- 周完成端点由现有交易日历/Session 决定；节假日短周不等于缺数，夜盘归属按 trading_day；未完成周排除。
- actual_dominant W1 继续采用完整周最后交易日的 rank1 合约及其整周事实；主力前同合约历史用于预热。
- W1 open/high/low/close、volume/turnover、末日 open_interest 沿用现有确定性聚合。
  收盘价与结算价不互换；成交额单位、单/双边口径、持仓量字段映射须在发现差异时核对来源证据。
- 价格、数量和成交额分别逐字段核对。精度处理必须有字段单位、来源表示和历史原始响应证据；
  任何舍入规则改变应版本化并列明 D1/W1 消费者影响，不能临时放宽阈值造绿。
- PRICE_UNAVAILABLE 必须由原始来源与完整端点证据确认；保留缺价事实、周线计算中断及后续重新预热。
  NO_TRADE 沿用既有严格定义。混合无交易/有效交易周若涉及改变聚合算法，单独提出真实样本和语义决策。
- 上市较晚或短主力段造成 NOT_APPLICABLE/WARMING 是合法结果；不能用跨合约拼接或缩窗使其 READY。
- 缺价前 CLOSED 保留；中断时 OPEN 标记 DATA_INTERRUPTED；后续 CLEAR 不能与断点前 BUILD 配对。
  数据历史修订会改变研究输入身份，不倒写旧 Signal/Event/参考交易证据，更不能推导真实账户成交。

## 5. 第一阶段：先得到可解释的差异清单

先选具有不同失败方式的样本：FG2309（新守卫冲突）、A2309（既有完整性错误）、
EC2610/RB2610/RU2605（通过 apply 后失败）、EG2309/EG2601（旧 partial）、
SI2310（缺价）、一个 REVIEW_REQUIRED 合约（例如 OI2611），以 FU/HC 作正常对照。

对每个异常周比较四份证据：已保存来源响应、当前 active D1、当前 active W1、按现有算法重算的预期 W1。
先读已有 journal、response 和不可变分区，不为诊断重复下载。旧响应可作为历史证据和隔离重放输入；
只有身份、覆盖、版本与来源合同完全验证后，才能纳入新的精确生产计划，不能当作新的来源请求授权。

差异项至少给出字段、日期、原值/新值、差额、单位、原始响应 hash、D1/W1 revision、日历端点、
本次是否已提交、影响消费者，以及“已证实根因/待证假设”。按实际受影响周去重，保留消费者引用。
核对样本后扩展至全部 102 个完整性异常合约及 24 个失败单元，避免以一个 turnover 样本解释所有错误。
结果直接挂到原生 audit/plan 的 diagnostics，不建第二套可执行修复真相。

出口：每个问题可归入可补缺口、来源修订、确定性转换缺陷、合法缺价、元数据问题或证据不足之一。
证据不足不进入写入队列；不能把设计的分类枚举当成已查明的生产数量。

## 6. 第二阶段：补齐恢复链路

### 6.1 规划受影响范围

在既有 planner 增加明确的数值冲突修复类型，与普通 missing-endpoint 分开。
从待修 D1 日期展开所有受影响完整周及 W1 月分区，跨月时包含两侧 D1，覆盖已存在的 W1；
再固定这些分区中需保留的其余行。将所有依赖分区的当前 revision/hash 与候选内容纳入计划身份。
如还影响 active continuous D1/W1 或其它消费者，先只读列出依赖；原 contract-warmup 不可隐式写 continuous。
确需扩大数据写入面时应形成新的精确范围，再决定执行。

### 6.2 同一候选 D1 生成 W1

对一个物理合约的有界修复单元，先取得全部计划内响应、验证身份与完整性，形成完整候选 D1，
再从这份候选 D1 确定性生成或验证 W1。旧的未变化 D1 只有在来源、质量与依赖证明成立时才复用。
若确需修订既有 D1，明确列出前后值、影响周线/策略与旧文件恢复指针，不能在“补周线”中隐含覆盖。
统一正常周聚合和 weekly_quality 的逐端点质量分类，避免 writer 与 reader 各自理解完整周。

先验证整个合约单元的最终候选状态，再激活任何分区；不再边下载下一组、边改变 active 数据。
对无法在资源预算内完整验证的单元，缩小为精确且依赖独立的范围，重新 prepare；不静默拆开共享周。

### 6.3 有界的 Catalog 统一激活

现有 store.publish 已能安装不可变文件且不改 Catalog；复用这一点，先落候选文件并做物理与来源验证。
在维护锁内核对所有旧 active 指针仍与计划一致，再在一个 PostgreSQL 事务注册本单元的 D1/W1 指针，
完成新视图的维护及质量读取验证，最后一次 commit。无需默认新增表、重型事务系统或删除旧文件。
此为对当前“单分区唯一可见点”合同的有界扩展，须同步 canonical 并做独立 Review。

Catalog 一次提交不能保证 consumer 多条 READ COMMITTED 查询天然看到同一快照。
消费者继续绑定已有 revision/snapshot token，验证本次读到的依赖集合一致；变化时显式拒绝该次结果。
只声称单个修复单元的 Catalog 激活原子性，不声称全数据湖、全品种或文件系统与数据库联合事务。

commit 前失败：active 指针不变，保留可检查的不可变候选；候选清理由独立精确清单处理。
commit 结果不明：停止写入，独立只读检查所有目标 old/new 指针；禁止推断失败后重试。
已确认提交但验收失败：保留失败事实。只有精确回退计划、旧文件验证及当前指针比较通过，且恢复授权覆盖时，
才可统一恢复旧指针；不能自动回滚覆盖后续合法更新。

### 6.4 完成标准

原生 apply 的成功应同时要求：候选来源与质量验证、物理回读、受影响 D1/W1 一致、
独立事务 consumer 读回以及重新规划无未解释差异。仅 replan 无 missing target 不能返回业务完成。
质量中断且证据完整可以成为正确处理结果，但不能伪装正常价格历史或策略 READY。
错误报告补足具体 week/field/revision 与已提交状态，避免全部折叠成 WEEKLY_SOURCE_BAR_CONFLICT。

## 7. 第三阶段：先小样本，再恢复逐品种队列

顺序：正常对照回归 → FG 一个冲突合约 → RB 一个完整但读回失败合约 → SI 一个缺价合约 →
跨月/历史 partial 样本。每一类都达到真实读回出口后，才扩大到同类问题；再沿 operational 顺序处理剩余品种。
7 个输入就绪品种保留回归，不重复补数。普通缺口按新的全量审计重新 prepare，旧计划与已完成批准不复用。

继续保留 owner 的执行方式：一个品种完成或遇到明确问题后进入下一个；不重试该品种。
工程实现、恢复证据和状态机收敛到现有 native campaign，去掉 task-local 脚本中 EG/SI 等硬编码恢复例外。
续跑需验证已完成前缀、回执、来源 journal、当前修订和剩余计划；成功、已知跳过、已知失败、未尝试、未知均有明确状态。
已知且不影响其他品种的失败可按批准边界继续；额度、共享身份、并发锁、证据不完整或提交未知停止受影响队列。
如果小样本发现新的共同实现缺陷，停止同类生产尝试，先修复和重测，避免再次把同一缺陷遍历 60 次。

批次预算需重新量化 provider 请求、预估/实际字节、分区数量、运行时限和 staging 空间；
本轮剩余 441/119 只是审计路由，不能直接作为新写入批准或来源费用承诺。

## 8. 验证与退出条件

| 阶段 | 必需验证 |
| --- | --- |
| 差异分类 | 四份证据逐字段一致性；日历/生命周期正确；正常对照无误报；重复消费者不重复计数 |
| 隔离实现 | 保存来源回放；Decimal 边界；跨月与节假日短周；D1-only 变化影响旧 W1；价格缺失与混合周；旧 W1 数值错但根数齐全 |
| 发布与恢复 | 最后一组验证失败时 active 零变化；候选落盘/注册/commit 前后故障；commit 未知；并发 revision 改变；重启和幂等；读者跨提交的一致性拒绝 |
| 真实小样本 | 精确 prepare/hash、真实候选、统一激活、独立 Catalog/文件/MDS/Newow 读回；D1 变化影响核对 |
| 全量输入 | 固定 as_of，60 品种完整盘点；所有依赖端点由有效 Bar、合法质量事实或正确不适用解释；预算耗尽为 incomplete |
| 产品闭环 | W1 60×3 状态正确及首次加载；D1 60×3 回归；reference/auxiliary/comparator 一致；READY、历史 PARTIAL、WARMING 分列 |

7/60 是严格历史输入就绪数，不要求最终所有合约历史都变正常。最终应分别交付“完整正常历史”、
“历史含中断但当前恢复”、“当前仍预热/中断”、“普通缺口/未解释错误”数量和明确名单。
合法短生命周期与 PRICE_UNAVAILABLE 不能为了 100% READY 被抹去。

本方案不因数据通过而自动开放 W1、发布 main/tag 或切换 Runtime；这些仍按对应精确版本和验收完成交付。
当前先落地 planner、候选校验和统一激活路径，限 `frequency=1w` 的物理合约恢复；生产恢复仍以精确新计划及逐品种读回为准。此阶段不变更策略公式、收益定义或运行版本。
