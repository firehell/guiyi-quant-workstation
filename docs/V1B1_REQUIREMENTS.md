# 归一量化 V1-B.1 需求文档

## 1. 阶段定位

V1-B.1 的阶段名称是：

```text
归一量化 V1-B.1：可信研究闭环收口阶段
```

V1-B.1 不是新功能扩展阶段，不是策略平台扩张阶段，也不是实盘准备阶段。它的目标是把当前已经基本跑通的 V1 Web 研究闭环收口为可审查、可复现、可浏览器验收的可信状态。

本阶段围绕焦煤 JM 最近 3 年真实 RQData / local standard parquet 数据，重点确认：

- 数据口径可信。
- 回测报告口径可信。
- 交易明细、资金曲线、回撤曲线与 summary 一致。
- Web 页面能真实展示核心闭环。
- K线上能定位买卖点。
- 单笔交易能进入复盘。
- 信号扫描只提醒，不触发任何下单逻辑。

V1-B.1 仍属于 V1 Web 研究闭环，不属于 V1.5 模拟账户阶段，不属于 V2 半自动实盘阶段。

## 2. 当前项目能力基线

本节以 `docs/PROJECT_CURRENT_SNAPSHOT_FOR_CHATGPT.md` 为主要依据。不确定、未浏览器验证、或文档与代码口径存在冲突的地方统一标记为“待确认”。

### 数据中心

当前已经具备：

- RQData / 米筐作为 V1 主数据源的项目口径。
- Local standard Parquet 作为 V1 本地正式数据湖。
- PostgreSQL 元数据表和 DuckDB 查询路径。
- 数据源、交易所、品种、合约、下载任务、质量报告、coverage 等 API。
- JM 1d / 15m / 5m / 1m primary 数据在项目文档中有覆盖记录。
- `MarketDataReader` 通过 PostgreSQL 元数据定位 Parquet，再用 DuckDB 查询 K线。

待确认：

- 当前本地数据库中的 JM 行数、质量报告和最新数据版本是否与文档快照完全一致。
- Web 数据中心是否能完整发起和追踪下载任务。
- 当前 Alembic head 与实际数据库状态是否一致。

### K线工作台

当前已经具备：

- `/market` K线工作台页面。
- `/api/v1/market/workbench/coverage` 和 `/api/v1/market/bars` API。
- TradingView Lightweight Charts K线展示基础。
- 前端指标工具支持 EMA、MACD、ATR 等计算。
- 回测交易明细可用于生成买卖点 marker 的代码路径。

待确认：

- 浏览器中 K线是否稳定显示。
- report_id 切换后 marker 是否刷新。
- 主图和副图十字星是否同步。
- 点击交易定位 K线的体验是否符合验收要求。

### 策略中心

当前已经具备：

- 当前 V1-B / V1-B.1 正式策略主线是 `jm_v1b_daily_direction_fast_entry`。
- 该策略围绕 JM，使用日线方向过滤，15m / 5m 独立入场，短持有和止损退出。
- `packages/quant-core/` 中存在策略代码和参数 schema。
- 苏冰 EMA21 相关代码、文档和 rulebook 存在。

当前边界：

- 苏冰 EMA21 是草稿 / 候选，不等同当前 V1-B.1 正式策略主线。
- `.agents/skills/su-bing-strategy/SKILL.md` 是知识资产和规则候选整理工具，不等同交易策略代码。
- 当前不做 Web 策略代码编辑器。
- 当前不做策略自动进化。

待确认：

- 前端策略中心调用的 `/api/strategies*` 与后端路由存在不一致风险。
- 正式策略版本表、策略版本治理和 Web 策略中心仍未形成完整产品能力。

### 回测中心

当前已经具备：

- FastAPI 回测任务 API。
- JM V1-B 固定任务 API：15m 和 5m。
- Redis / RQ worker 执行回测任务的代码路径。
- vn.py CTA BacktestingEngine 适配路径。
- 回测结果入库模型，包括报告、交易明细、委托、资金曲线、回撤曲线。
- 回测报告列表、详情、交易明细、委托、资金曲线和回撤曲线 API。

待确认：

- 非 inline RQ worker 在当前本地环境中是否能稳定执行。
- 当前最新报告的 summary、trades、equity curve、drawdown curve 是否完全一致。
- 旧自研回测引擎与 vn.py runner 的边界是否已在执行口径中清晰隔离。

### 报告中心

当前已经具备：

- `/backtest` Web 页面。
- 回测报告详情展示。
- 交易明细展示和导出 API。
- 资金曲线和回撤曲线 API。
- 报告字段中已有年化收益、最大回撤、手续费、滑点、保证金、胜率、盈亏比、连续亏损等口径的代码或字段基础。

待确认：

- 年化收益口径是否与资金曲线和持仓周期一致。
- 最大回撤金额、最大回撤百分比与 drawdown curve 是否一致。
- summary 与 trades、equity curve、drawdown curve 是否完全一致。
- Web 展示字段含义是否与后端字段含义一致。

### 信号扫描

当前已经具备：

- 信号扫描 API。
- JM V1-B 专用扫描逻辑。
- 信号扫描任务表、策略信号表和通知记录表。
- `/signal` Web 页面。
- WebSocket / 轮询相关代码路径。
- 项目规则明确 V1 信号扫描只提醒，不下单。

待确认：

- 非 inline RQ worker 执行信号扫描的完整链路。
- 任务状态从创建到完成 / 失败的实际流转。
- 信号是否写入数据库并能在 Web 展示。
- 当前是否有真实触发信号样本。

### 复盘中心

当前已经具备：

- `/review` Web 页面。
- 复盘 API。
- 从回测交易创建复盘 note 的 API。
- 复盘标签 API。
- 复盘统计和附件记录模型。

待确认：

- 点击交易后是否能稳定定位 K线。
- 单笔复盘 note 创建后的 Web 回显是否符合预期。
- 复盘标签是否能正常读取和用于记录。

### 风控

当前已经具备：

- 回测和信号模型中已有手续费、滑点、合约乘数、保证金、单笔风险、最大回撤、连续亏损等字段或计算基础。
- 交易参数 resolver 用于解析合约交易参数。
- 策略、回测、信号的项目规则要求默认检查未来函数、数据泄露、过拟合、成本、保证金和回撤。

待确认：

- 风控中心作为独立产品模块尚不完整。
- 单笔风险、最大保证金占用、最大连续亏损等是否已在所有报告口径中一致使用。
- 回测报告不应被解释为模拟盘或实盘准入结论。

### 实盘边界

当前项目边界：

- V1 不接实盘。
- V1 不下单。
- V1 不做 CTP 实盘。
- V1 不做天勤实盘。
- V1 不做 AI 自动下单。
- 信号扫描只提醒，不触发订单。

待确认：

- 配置模板中的 CTP、天勤、TuShare 等候选字段是否仍只作为禁用候选占位。
- 代码库中不得写入任何账号、密码、token、license、API Key、米筐账号、天勤账号或 CTP 密码。

## 3. V1-B.1 总目标

V1-B.1 完成后，最终用户应该能够在本地完成以下可信研究闭环：

```text
启动本地系统
→ 查看 JM 数据覆盖
→ 创建 15m / 5m 回测任务
→ worker 执行回测
→ 查看可信报告
→ 查看交易明细
→ 在 K线上定位买卖点
→ 做单笔复盘
→ 运行信号扫描
→ 在 Web 查看信号
```

该流程必须使用 RQData / local standard parquet 的正式数据口径，回测报告必须入库，Web 展示必须能被浏览器级 smoke 验收。

## 4. P0 需求：项目可信状态恢复

目标：先让项目状态可解释、可继续开发、可被外部审查。

需求：

- 工作区清理：执行 `git status --short`，确认所有未提交修改来源。
- 被删除测试文件确认：任何测试文件删除都必须说明原因，不能让测试删除状态污染验收判断。
- git checkpoint：在进入业务修改前由用户或 Cursor 建立可回退 checkpoint。
- 测试基线恢复：恢复或确认后端 pytest、ruff、前端 build 和指标测试的基线。
- 敏感配置不进入文档和代码：不得写入 `.env`、账号、密码、token、license、API Key、米筐账号、天勤账号或 CTP 密码。
- 当前上下文入口统一：后续上下文先读 `docs/PROJECT_CURRENT_SNAPSHOT_FOR_CHATGPT.md`，再读 V1-B.1 需求和验收文档。

完成效果：

- 当前脏工作区有解释。
- 删除文件有结论。
- 后续 Agent 不会基于不可信 diff 继续开发。
- 文档、测试、回测报告和 Web smoke 的验收入口统一。

## 5. P1 需求：回测报告口径加固

目标：让回测报告成为 V1-B.1 最可信的事实源。

必须加固和验收的指标：

- 年化收益。
- 最大回撤金额。
- 最大回撤百分比。
- 手续费。
- 滑点。
- 保证金占用。
- 连续亏损。
- 胜率。
- 盈亏比。
- summary 与 trades 一致。
- summary 与 equity curve / drawdown curve 一致。
- Web 展示字段含义一致。

口径要求：

- `summary.total_net_pnl` 必须能由逐笔交易汇总解释。
- `summary.total_commission` 必须等于逐笔交易手续费汇总。
- `summary.total_slippage` 必须等于逐笔交易滑点汇总。
- `summary.final_equity` 必须等于 equity curve 最后一项。
- `summary.max_drawdown` 和 `summary.max_drawdown_pct` 必须能由 drawdown curve 解释。
- 胜率、盈亏比、最大连续亏损必须能由逐笔交易统计复算。
- Web 页面不得用不同含义的字段展示同一个指标名称。

## 6. P2 需求：Web 浏览器级 smoke

目标：确认核心研究闭环不是只有 API 和数据库存在，而是能在浏览器中被用户使用和检查。

必须验收页面：

- `/backtest`
- `/market`
- `/review`
- `/signal`

必须检查：

- 页面是否能打开。
- API 是否 404。
- 控制台是否报错。
- report_id 切换是否刷新。
- K线是否显示。
- 买卖点 marker 是否显示。
- 十字星是否同步。
- 交易明细是否可读。
- 复盘是否能定位交易。
- 信号是否能展示。

完成效果：

- 每个页面都有截图证据。
- 每个页面都有 API / 控制台检查结果。
- 核心闭环页面不依赖肉眼猜测或文档声明验收。

## 7. P3 需求：信号扫描 worker 联调

目标：确认信号扫描能通过真实任务队列执行，而不是只依赖 inline 或手动路径。

需求：

- 非 inline RQ worker 执行。
- 任务状态流转。
- 信号写入数据库。
- Web 展示信号。
- 不触发任何下单逻辑。

完成效果：

- 能创建信号扫描任务。
- worker 能消费任务。
- 任务能进入成功或失败终态。
- 产生的信号可通过 API 和 Web 查看。
- 全链路只提醒，不生成订单、不连接实盘、不调用 CTP / 天勤交易接口。

## 8. P4 需求：策略中心边界收敛

目标：让策略中心在 V1-B.1 保持清晰边界，不把候选知识和后期能力误写成当前能力。

当前口径：

- JM V1-B 是当前正式策略主线。
- 苏冰 EMA21 是草稿 / 候选。
- 苏冰 skill 是知识资产，不等同交易策略代码。
- 当前不做 Web 策略编辑器。
- 当前不做策略自动进化。

后续策略开发流程：

```text
Strategy Spec
→ 审查
→ 实现
→ 测试
→ 回测
→ 复盘
```

边界要求：

- 不能把苏冰 rulebook 里的规则候选直接写成买卖信号。
- 不能从旧策略代码反推课程规则。
- 不能默认继承旧 `SU_BING_QUANT_SPEC_V0_1.md`。
- 新策略必须先有独立 Strategy Spec 和审查结论。

口径：

- `docs/PROJECT_CURRENT_SNAPSHOT_FOR_CHATGPT.md` 是当前上下文入口。
- 历史文档只作为历史参考。

## 10. 明确不做的需求

V1-B.1 明确不做：

- 全自动实盘。
- CTP 实盘。
- 天勤实盘。
- AI 自动下单。
- 策略自动进化。
- Web 策略代码编辑器。
- 多账户管理。
- 云部署。
- 手机 App。

同时不做：

- tick 级高频回测。
- 复杂盘口队列撮合。
- 多用户权限。
- 公开 SaaS。
- 无风控拦截的交易执行。
