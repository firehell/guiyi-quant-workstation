## 3. G1：先解决审计不产出有效报告

### 3.1 只读取证，不重跑生产审计

- 核对原任务实际 cwd、commit、Python executable、导入模块路径、console-script 与模块入口。
  比较当前代码与失败时 exact commit，不把另一工作树或另一环境的结果归于该次尝试。
- 核对宿主工具 session/command 的状态含义；工具输出缺失或 exit=-1 不能自动解释为业务退出码。
- 在已知原输出目录、指定共同 evidence 根及原执行记录中定位产物；只扫描相关路径，
  不搜索/输出生产凭据，不广泛遍历用户目录，不因文件未找到而自行重建“历史成功回执”。
- 只读核对旧审计进程/锁是否仍存在。若无法确定，记录未知，禁止重复启动、杀进程或接管 attempt。
- 配置核验只使用既有安全 loader，记录 hash/根身份和必需项是否齐全；不打印值，不修改 project.env。

### 3.2 按已证明根因做最小工程修正

优先检查现有 `app/guiyi_cli/main.py`、`data_commands.py`、`output.py`、
`newow/readiness_composition.py`、只读事务以及既有进程输出/证据写入能力。
只有实际复现需要时才修改；不预设要创建另一个 audit 平台、wrapper 或 writer。

- 使用现有 fixture 与注入的 session/readiness builder，真实子进程验证正式入口被调用。
- 临时目录中覆盖：正常完整报告、非法参数、预算耗尽、异常、取消/超时、写入失败、空输出、截断 JSON。
- 报告数据与进度消息分流；记录真实退出码和可脱敏的错误。无有效结构化报告时不输出完整性成功。
- 若需新增显式文件输出，优先在唯一既有入口上实现：输出在受限目标目录内，临时文件完整写入、
  关闭并校验后原子发布；拒绝覆盖、符号链接和跨根路径，不能把 stdout 重定向创建的空文件当成功。
- 外层进程时间预算须覆盖原生 audit deadline 与有界收尾；宿主短次 yield 不等于终止或重新启动。
  长进程用已有 session 等待结果，返回进度时继续同一进程，不主动重新发起命令。
- 提前用原生 fixture 验证零普通目标的 prepare→独立验收全链路。当前 verifier 要求 execution 与关联证据，
  因此不能现场伪造空执行回执；若零目标路径有工程缺口，在 G1 最小修正并测试，冻结真实代码身份后再进入现场。
- 测试证明零 provider/生产写入；实际数据审计仍等待 G2 的单独意图。

### 3.3 工程和文档收口

- 复测两项既有工程失败，按当前合同定位原因。修正固定 high 的过时断言时不得修改权限/模型配置；
  不得删掉整条安全测试。旧已跟踪计划先核对归属、引用与是否仍被其他任务使用，不能直接删除凑绿。
  若修正超出批准范围或会改动他人文件，保留该项待决，并准确说明是否阻塞候选。
- 在原任务 review 中追加实施事实、已确认根因/仍未知项和验证结果，保留旧历史。
  正确回填 Task 1–4 已验证项，不勾选尚无证据的真实操作。
- 执行命令集中更新 TESTING；按变更跑定向测试、必要模块测试、lint/type、OpenSpec、secret scan 和 diff check。
- 独立 Review 重点检查退出码、空/损坏输出、真实路径身份和失败后不重试；有问题先修再复核。
- 已批准的普通工程可完成 commit/push 与 develop 集成。现场使用完成集成后的干净 exact 执行根，
  不在持续变化的 develop 中边改代码边执行冻结包。

G1 可以关闭的结论是“审计入口及结果捕获在隔离环境验证通过”；生产故障未充分取证时仍标原因未定，
不能把隔离通过追溯成对旧现场的唯一根因证明。未解决且妨碍可靠审计的问题必须保持 G1 未完成。

## 4. G2：完整审计、准备、一次 apply 和独立数据验收

### G2-A 新现场只读意图

向 owner 提供具体的工作站、exact 代码根/commit、固定 as_of、operational 集合/hash、仅 D1、
consumer/window、审计预算和输出根。明确此次只读是否包含 prepare 所需 Catalog/planner 访问与证据文件生成。
旧任务的审计和 apply 批准不跨会话复用。默认不沿用 9 月 15 日截止时刻；先由本次审计用途确定
新 cutoff 并冻结，如果只是复现旧现场则使用旧 cutoff并明确不能代表最新可用性。

1. 核对 W1/D1/60m writer 和自然维护窗口；共享真实操作串行。锁忙退出待验，不循环等待抢锁。
2. 只运行一次完整 dependency-only D1 audit；保存原始完整报告、身份、开始/完成时点和真实终态。
3. 先校验非空、JSON/schema、complete=true、budget_exhausted=false、readonly=true、
   provider_requests=0、writes=0、matrix=false、frequency_scope=[1d]，以及原生全量枚举与 metadata 状态。
4. complete 只表示盘点完整；SOURCE_EXCEPTION/INTEGRITY_ERROR/REVIEW_REQUIRED 不等于数据通过。
   报告不足不能拆掉失败品种、扩大预算自行重跑或用旧余额补齐；预算/范围变化须重新明确意图。

### G2-B 自动 prepare 和具体审批包

输入必须是 G2-A 完整原生报告及 hash，复用已实现 campaign prepare，不手写缺口名单。
正常每子包最多 20 单元；一个总包内的正常子批按已批准 policy 连续运行，不逐批反复索要同一授权。
证据根使用可持久保存、不会随 task worktree 清理的已确认位置；不得自行修改生产根或放宽路径约束。

审批包只汇总现有报告/manifest，不新增另一套事实源，必须包含：

- 源报告 SHA、固定 as_of/消费者窗口、品种/hash、代码/digest、配置/Canonical 身份；
- 总包及全部子包的 hash、顺序、精确物理合约/月分区/缺失集合和单次 attempt 身份；
- 普通目标与来源异常/待审集合，单元/分区/端点/请求分别计量，保持完整分母；
- 预计请求数，资源/维护窗口约束；字节预算只使用有效测量或明确保守估计，不把本地文件大小当 RQData 额度；
- 续行 policy、失败停止条件、已提交分区保留方式、只读对账方式和下一次必须重新授权的条件。

quota 查询若需访问真实 provider，应包含在明确范围中；不能为了审批包估算先做未授权“试下载”。
若字节上限必须技术强制而现有编排没有对应守卫，先完成可审实现与测试，重新冻结包，再申请执行。
0 普通目标时不制造空 apply；保留来源异常并走现有只读验收路径，若该路径未兑现则先定向修正工程。

### G2-C 精确 apply 意图与失败处置

owner 批准具体 campaign hash、attempt、代码根、数据范围和 policy 后，首次执行前重新 preflight；
任何漂移在 provider/写入前停止，不自动 reprepare 后套用旧批准。

| 运行结果 | 处理 |
|---|---|
| 正常成功 | 保留 journal 与每单元 strict-read/replan，继续已批准的下一正常批次 |
| 严格零提交的白名单来源异常 | 只有本包 policy 明确允许且全部证明满足时隔离并继续；隔离不是修复成功 |
| 部分提交、额度/网络/锁/身份失败 | 停止并保留合法已提交事实；只读核对，不重试、不回滚数据 |
| 提交或进程结果未知、缺 journal、保存失败 | 停止；不知道是否执行的单元不能写成 unattempted；先独立对账 |

随后运行既有独立 D1 verifier，冻结同一 as_of，覆盖可能已处理单元及完整 operational 范围。
父执行成功而最终 audit 失败，保留已知成功，但输入验收未完成。结果未知不会被“当前读到数据”自动消除。
再次只读验证使用新的明确观察意图/唯一 observation，不能覆盖旧报告或自动重启 apply。

### G2-D 数据通过标准

原始承诺范围逐项输入可用，原生剩余目标/未解数据异常与未知为零；chart、auxiliary、reference 生命周期
和 comparator 所需输入都可证明。三策略共享同一依赖不意味着三次重复下载。
明确区分行情可用与比较器研究证据是否充分；后者不足可如实展示，但不造价或改公式。
若数据源异常无法满足，G2 保持 PARTIAL/BLOCKED，单独呈现确切合约/日期/原因和可行选项；
缩范围或带不可用状态发布必须由 owner 明确改变验收合同后重新审查，不能自动视为达标。

## 6. G4：发布、Runtime 与自然业务验证

按 [发布技能](../../../.agents/skills/release-agent/SKILL.md)、[部署合同](../../../deploy/README.md) 执行。
先核对本版完整 develop 差异中是否含其他任务，不能把它们隐藏在“D1 发布”名下。

不在 D1 的 Release Gate 中隐含完成 W1 发布。

1. **候选审查完成后申请 Release Gate：** exact candidate、版本/差异、验证结果、未完成项和兼容回退准备。
   批准后才执行一次 main merge、annotated tag、GitHub Release，分别读回对应身份。
2. **另申请 Runtime Gate：** 先完成可做的只读 render-only/preflight、精确服务差异及回退兼容性核验，
   连同指定工作站、exact tag、服务范围和维护窗口供 owner 审批；不能提交空泛切换请求。
   获批后重验具有时效性的现场条件，再按既有顺序切换；失败按合同停止，不自动重试或擅自回退。
3. **即时读回：** 服务 root/commit、API/Web 版本和真实 D1 页面；不变更 Scope、收件人或可选定时任务。
4. **自然验收：** 根据实际影响观察下一次自然 D1 更新、对应完成日的 MDS/页面增量、必要 Live/heartbeat，
   以及此次发布真正要求的既有自然维护证据。没有发生的场景保持 pending，不能手工造 Bar 或回执。

只有 release 身份通过才写 RELEASED；只有本版必需 Runtime 自然证据通过才写 RUNTIME_READY。
若等待未来交易日，保留可恢复检查点并等待，不刷屏轮询；需要跨会话定时检查时先按工具规则明确建立跟踪任务。
G4 未通过不能用“Goal 已完成”结束整个交付。60m、完整解释、因果研究/账户演进均不自动加入本方案。

## 7. Sol medium 的执行方式
