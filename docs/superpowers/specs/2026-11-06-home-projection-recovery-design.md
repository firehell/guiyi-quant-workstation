# 首页策略摘要的故障隔离与自动恢复方案

状态：设计提案，尚未实施或启用新的后台任务。owner 要求自行排查并完整设计，目标是消除摘要失败后长期无法自行恢复、原因不明的使用问题。

## 1. 结论与证据边界

这不是仅改提示文字或发布一次摘要就能闭合的问题。现实现有四个可确认的缺口：未来元数据变化也会使历史摘要失效；构建失败缺少可重现上下文；失败/来源变化没有独立、可恢复的后续处理者；浏览器读请求失败或轮询耗尽后可能停止刷新。

截至本轮开始，实际 v97 首页接口 HTTP 200，54 个品种 ready，PF/PR/PX/RS/SF/SM 六个品种 failed。它们的持久记录都是 D1 `HOME_PROJECTION_BUILD_FAILED`，没有保存原异常类型、步骤、失败时来源身份或失败时刻。该码不能区分程序异常、数据库驱动异常等情况。旧失败不能事后改写成某个猜测的原因。

已经完成的检查：

- v95 与 v96 的 `home_projection.py`、`home_projection_composition.py`、`snapshot_cache.py` 内容相同。
- 使用正式 v96 计算函数、原 operational 顺序、固定 2026-11-06 18:07:49 北京时间做 60 品种 × D1/W1 的独立只读计算：120/120 成功，累计计算约 425 秒，测试前后来源版本一致。
- 原持久摘要在 18:18 已处理到最后一个品种 ZN；18:24 的只读 Python 栈停在 `_retained_size -> SnapshotCache.put -> ProductService.query`。代码调用顺序是先摘要构建、后消费者核验，不能把后续卡顿或随后 SIGTERM 直接认定为六次摘要失败的原因。栈本身也不足以证明缓存算法存在无限循环。
- develop `b8760f264` 已增加安全错误位置、步骤及异常类型日志，定向 18 项测试通过；它尚不提供持久重试或自动恢复，不能称为故障根治。
- 本轮以正式 v97 的原 `HomeProjection.build()` 做全入口构建，输出只写独立临时目录：120 项计算全部成功、243 次来源检查，耗时 543.458 秒；但来源在构建中变化，最终 2 ready / 57 stale / 1 failed（V，`HOME_PROJECTION_SOURCE_CHANGED`），概览 stale。这是真实的发布有效性失败，不能计作全入口通过。
- 另将真实线上摘要复制到独立临时文件，调用原 builder 重建六品种：12 项计算成功、26 次来源检查、54.933 秒，原六条计算失败标记已清除；最终仍因同期来源变化只有 4 ready / 56 stale。没有覆盖线上文件。
- 只读 Catalog 查到 20:30 新变更：60 条 MainContractMap 的交易日都是 **2026-11-09**；225 条新增 Session 的有效日都是 **2026-11-10**。这晚于当前已确认的 Nov6 日线/完成周。同期新增 Dataset/Partition 为 1m/5m；现摘要本来已经排除这些频率。实际 `catalog_versions()` 却未对 mapping/session 限定消费时间范围，未来记录会进入历史 D1/W1 的全行指纹，足以使这些历史摘要失效。没有保存每个旧组件指纹，不声称排除了其他同期变更。
- 20:34 正式 API 再读 HTTP 200，状态变为 54 stale / 6 failed，正式摘要生成时间仍为 18:17:42。临时诊断没有更新该正式资产；这也实际验证了来源失效后没有自动接续发布的现场状态。

首次六条通用异常没有完整上下文，当前测试也没有复现，因此首次失败的具体异常仍未知。此次完整入口已经复现出另一条确定路径：未来元数据更新触发全市场历史摘要失效，构建中变化被正确拒绝，但无人自动接续。以下设计同时修复该失效范围和恢复/诊断缺口；不能把本次 V 的明确错误改写成旧六条通用错误的原因。

依据入口：`openspec/specs/market-home-overview/spec.md`，`docs/ARCHITECTURE.md` 的首页持久投影约束；实现位于 `services/quant-api/app/market_data/newow/home_projection*.py`、`after_market.py`、`snapshot_cache.py`、`apps/quant-web/src/components/market/MarketHomeStrategyCards.vue`。

## 2. 目标与边界

验收目标：

1. 可恢复的计算、进程和网络故障自动恢复，不依赖用户手动刷新或第二天盘后任务。
2. 任一品种失败、超时或子进程崩溃，不阻塞其余品种发布；没有实际所有者时不长期显示“计算中”。
3. 无论成功、失败或中断，都能确定具体品种、周期、代码身份、目标来源版本、失败步骤及最近一次真实尝试。
4. 来源稳定且依赖健康时，60 品种完整构建目标在 20 分钟内完成；网络恢复后，可见页面在 60 秒内恢复读请求。超过目标必须反映为未完成，不伪造成功。
5. 当前六品种的历史可验证事实保留；新结果通过完整校验并实际发布后才能清除对应失败状态。

不改变策略、参考收益、成交、风险、账户或换月语义；不新增 RQData 下载、Canonical/Catalog 写入、通知或交易；GET 保持纯读取，不变成按访问触发的重算接口。保留 completed-only、strict-before、物理合约及现有来源质量合同。

本轮只交付设计，不切换运行副本，也不启用新的 worker。这里的新运行职责与重试合同需在后续实施时明确更新 canonical，并纳入现有部署绑定与恢复检查。

## 3. 方案比较与推荐

| 方案 | 优点 | 无法满足或代价 |
| --- | --- | --- |
| 只补日志、在现有盘后调用内重试 | 改动少，无新运行项 | 盘后进程退出或错过运行后，仍无人接管；无法满足及时自动恢复 |
| 首页 GET 遇到失败就触发计算 | 看起来直接 | 访问量决定重算，违背只读合同，冷打开慢，并发和认证重试可放大计算；排除 |
| **一个本地受监督的摘要恢复执行者** | 与行情维护、API 和消费者核验隔离；可重启接管；统一处理手工和自动构建 | 多一个轻量 launchd 运行项，需要明确持久状态、预算和部署身份 |

推荐第三种。这是本设计的工程建议，并非 owner 已批准新增运行项。继续采用模块化单体，复用现有构建和行情入口，不引入消息队列、微服务、PostgreSQL 新表或迁移。只有该执行者拥有正式摘要发布职责，避免盘后、CLI、API 各自维护一套 writer。

## 4. 唯一构建与恢复入口

先修正来源身份范围：

- 增加明确的 `home_source_identity_v2`。将“当前应有的 completed 截止身份”与“实际历史计算依赖身份”分开，最后共同决定 ready。
- 历史依赖范围复用现有 reader/MDS 的依赖证明和预热范围，不自行猜测合约、交易日或 cutoff。Mapping 只包括实际历史消费范围；Session 只包括与该范围相交的有效版本。Calendar 必须覆盖现有周完成性判定需要的完整日历窗口，不能粗暴只截到周五；无从证明范围时继续保守失效，不能漏掉依赖。
- 依赖证明同时覆盖 resolver 的**候选选择范围与缺失事实**，不能只记录最终回退后消费的行。最新应有候选尚缺映射/分区时，其存在性查询范围仍属于依赖，随后补齐必须触发重新评估。W1 resolver 实际使用的 `publication_state_from_status()` 及其有效时间边界也属于选择依赖；仅发布状态改变也可能改变是否允许回退。复用该权威函数输出的规范化意义，不将整个状态文件、mtime 或无关心跳写入指纹。
- Builder 保存有界的消费与选择依赖描述，包含查询范围而不只是当时已存在的 id 列表。GET/空闲检查仅用轻量 Catalog 查询和已声明的发布状态/时钟边界重新验证；不为计算指纹读取 Parquet 或运行 resolver 回放。旧资产缺少该描述时保留历史，排队初始化，不能在 GET 中现场补建。范围内新出现的行和“缺失变存在”必须被捕获。
- 指纹仍使用范围内的完整相关行版本、物理分区/质量/输入身份。历史同数量修订、已消费映射变动、历史 Session 更正、公式或实际完成日变化必须失效；不以 max 时间、计数、TTL 或跳过校验换取稳定。
- 仅追加/改写与当前消费范围无关的 Nov9 映射、Nov10 Session，不应让 Nov6 的已确认 D1/完成周重新计算。DB MVCC snapshot 仍可使指纹缓存重新评估，但评估后的相关依赖 hash 应保持不变。
- 这是现有“全相关行”合同的范围精化，必须更新 canonical，并以未来元数据不影响历史结果、历史更正仍正确失效两组独立测试证明。不能将未来元数据视为价格事实，更不能为此关闭元数据准备。

链路：

```text
行情正式发布 / 应用计算身份变化
    -> 轻量来源检查，找出与 last-good 不匹配的品种
    -> 持久记录有界待办
    -> 摘要执行者运行隔离计算
    -> 来源和结果复核
    -> 单品种完整代次原子发布
    -> GET / 浏览器读取并自动恢复
```

- 现有盘后行情成功仍先持久化原成功状态，然后只发出摘要刷新请求，不再同步执行重型摘要与恢复逻辑。
- 新执行者是一个受监督的本地运行项：启动时恢复未完成工作，空闲时每 60 秒做轻量来源/待办检查。没有变化时不读 Parquet、不回放策略、不写摘要。
- 盘后刷新请求用于及时唤醒；即使该请求与进程退出之间发生中断，启动/定时版本比对也能发现漏项，不依赖一次易丢失的内存信号。
- `guiyi home build` 与自动入口调用同一执行模块。对正式目标，CLI 请求该唯一所有者并可等待结果；对显式开发/临时目标，可使用同一执行模块独立构建。目标路径、数据环境和所有者锁必须隔离。
- 消费者核验仍是独立只读检查，失败不更改摘要构建结果，也不能占用摘要 worker 的发布锁。它的业务结论不由摘要 ready 替代。

## 5. 数据与生命周期

继续保留一个正式 last-good 摘要资产；在同一派生根增加一个**有界工作状态文件**。这份状态是进程恢复所必需的运行状态，不是新的行情或交易权威，也不为每条命令生成一套 report/receipt。

工作状态包含最多 60 个品种工作项及一个概览工作项：

- `job_id`：品种、D1/W1 目标来源版本、目标交易日/完成周、计算/展示身份的 hash。
- `generation`、所有者实例及运行 commit，阻止旧执行者或晚到子进程覆盖新工作。
- `pending/running/retry_wait/succeeded/blocked/superseded`、尝试次数、开始/截止/下次尝试时间。
- 最近三次尝试的结构化诊断：异常分类、安全错误码、阶段、文件名/函数/行号、耗时、来源身份、已解析时的输入 hash。不得保存原异常文本、SQL、凭据、locals 或绝对私有路径。

两个文件都使用大小/schema/hash 校验、禁止符号链接、临时文件 + fsync + 原子替换。先持久记录 running，再启动子进程；先原子发布摘要，再记 succeeded。两文件不假装存在跨文件事务：若在两步之间崩溃，恢复者校验真实摘要内容及来源身份后补记成功；不根据一次历史状态直接认为发布成功，也不盲目重算。

同一 job 的累计失败计数不因浏览器刷新、worker 重启或重复入队归零。来源/相关计算实现身份真实变化生成新 job，旧失败保留为历史尝试，不冒充新版本当前失败。实现身份使用相关计算/构建模块的明确版本或发布内容指纹；不相关模块发布不使全部健康摘要失效。运行 commit 仍逐次记录。新 job 不得无限重置品种及全市场资源预算。

持久工作状态限制 256 KiB；last-good 继续沿用现有 2 MiB 上限。有限历史保留在既有轮转日志中，不能通过无限追加把状态文件变成账本。

## 6. 计算、发布和超时隔离

- 每个品种的 D1/W1 是一个发布单元；任一周期失败就保留该品种上一完整代次。源版本未变的周期可复用，但提交时必须一起验证，不能把不一致的新旧周期包装成当前综合结果。
- 子进程只读数据库/Canonical，只写其独占临时结果；正式文件仅父执行者可提交。计算仍调用现有 resolver、ProductService 和 Reference 投影。
- 初始并发上限 2；每周期墙钟预算 120 秒，低于现 canonical 600 秒上限。正常工作负载须以真实 120 项构建证明预算足够；若不满足，先按阶段定位，再在既有上限内确定预算，不能静默缩窗、降低质量或改公式求通过。
- 墙钟上限由父进程强制执行，不依赖计算函数偶尔检查 cancelled。到期先 TERM，5 秒宽限后仍未退出才对本任务可验证身份的子进程终止；保留 timeout 事实。子进程不能持有正式 writer 锁，旧子进程的输出必须经 job/generation 检查才能接纳。
- 父执行者重启时先核对其持久登记的子进程出生身份与工作身份，处理本任务遗留进程；不能按模糊命令或裸 PID 杀进程。必须用故障注入证明没有孤儿进程和跨代提交。
- 计算前捕获来源身份，计算使用只读事务及固定 as_of；提交前再次核对对应品种来源、计算身份和父所有权。来源变化时废弃临时候选并更新待办，绝不把旧代结果称为当前。
- 维护锁被占用、数据库不可达或来源不可验证时保留 last-good，延期处理，不读取未经确认的中间态。只在发布前短时验证门禁，不让重型计算长期占住行情维护锁。
- 概览有独立工作状态和预算，失败不得挡住 60 个品种摘要；品种成功也不冒充概览成功。

缓存卡顿作为独立实证风险处理：将 `_retained_size` 改为有界遍历，达到既有字节上限、节点或耗时预算立即放弃缓存接纳，不影响已完成计算的正确结果；初始评估上限为单次 2 秒/100 万节点，须用真实结果基准验证正常接纳率和内存预算。缓存拒绝不能制造新 token、续期失效 token 或放宽 proof 校验。这个改动需针对性独立 Review，不能以已观察的栈冒充它已被证明是六次失败根因。

## 7. 自动恢复规则与预算

| 分类 | 恢复方式 | 停止条件 |
| --- | --- | --- |
| 临时数据库连接失败、明确可恢复的只读事务失败 | 新只读事务/新子进程，30 秒、120 秒后重试；每轮最多三次尝试 | 本轮耗尽进入 dependency_wait，按下述依赖恢复规则重新取得有限资格 |
| 未分类程序异常、无法证明原因的子进程退出、硬超时 | 最多一次全新子进程复验，保留两个失败位置 | 同来源/相关代码身份重复失败则 blocked；不能因依赖探测成功自动解封 |
| 构建期间来源改变 | 候选不发布；两次间隔至少 30 秒的轻量来源检查一致后合并为最新 job | 每次调度至多三次改版接续；仍不稳定则 source_unstable，60 秒后重新轻量检查，不忙循环 |
| 数据不足、质量失败、映射/Session 不可验证 | 保留历史事实，明确缺少的权威事实 | 不对相同版本反复计算；相关来源身份变化后自动重新评估，不自动下载修复 |
| 锁被占用、前一个有效执行者仍在工作 | 下次轻量检查，保持原 job | 不产生第二个 writer，不消耗计算尝试 |
| 完整发布成功并读回 | 工作项 succeeded，更新实际截至时间 | 只有真实发布成功才清除当前失败 |

机器可恢复类别使用明确 allowlist；不把所有 `Exception` 都视为网络故障。数据库类别基于驱动类型和 SQLSTATE 分类，但公开状态只给安全业务码，不输出驱动文本。

恢复轮次与预算精确定义如下，全部持久化，worker 重启不重置：

- 一轮是同一品种、job、依赖恢复资格下的最多三次临时故障尝试。三次耗尽后至少冷却 15 分钟；共享的依赖探测每 60 秒至多一次，仅执行有界只读连接/必要来源验证，不运行策略。冷却结束且连续两次探测成功，才能开启新轮次。故障一直持续则不做计算尝试。
- 每品种跨所有 job，每个固定 UTC 自然小时最多六次实际计算启动、累计子进程占用最多 360 秒；并发以实际占用分别计时，两个子进程各跑 10 秒计 20 秒。不能以来源小幅变动或 worker 重启绕过。临时故障资格在下一小时预算恢复且探测通过后可自动接续；确定性错误/未知重复错误不因小时变化或 SELECT 1 成功解封。
- 全市场同一自然小时划分首次构建预算 1200 子进程秒和恢复预算 600 子进程秒。该小时每品种首次调度按轮转公平执行，来源更换不重新获得“首次”资格；同一品种的后续尝试计入恢复预算。首次预算不能被重试借用，恢复预算用尽不阻塞其他品种首次构建。单次正常全市场批次 20 分钟是服务目标，不是删除未完成工作或重置预算的时点。
- 小时边界、已消耗时长和已启动次数持久化；启动前保守预约本次上限，退出后凭可验证结果结算。跨小时执行分段计费；时钟回拨不额外补充预算。来源稳定后的 20 分钟目标以依赖健康且有相应计算预算为前提，预算等待必须在状态中明示。
- 新来源或相关计算实现变化能解除旧数据/代码失败的资格限制，但仍服从小时资源上限；同版本的业务合同错误不由通用健康探测解封。来源持续抖动只做低频检查，正常品种先处理，不让一个品种反复占据两个计算槽。

## 8. 页面读取与状态表达

前端分别管理传输状态和已发布事实状态，不再把两类错误合并成同一句。

- 网络/5xx/超时：保留已验证缓存，按 2、5、15、30、60 秒退避重新 GET；后续上限 60 秒，成功后复位。每个可见市场页面最多一个在途摘要请求。
- 页面隐藏或离开市场时取消请求/定时器；返回可见、浏览器 online 或用户手动刷新时立即读一次。取消不是失败，旧 generation 响应不得覆盖新状态。
- 对 401/403 不循环重试认证，也不绕过权限；明确需恢复访问。无效响应保留已验证事实并标记协议异常，采用低频读回，不能接纳坏内容。
- 已知 worker 在恢复时显示“2 个品种更新中，暂用截至……的摘要”；真实 blocked 时显示品种、失败类别、截至时间和最近尝试时间。没有 last-good 的行明确显示暂无已验证摘要。
- 当前板块提示只统计当前可见品种；若给全市场计数，明确写“全市场”，不能让其他板块的一条失败看起来是当前所有行都失败。
- 即使超过五分钟，可见页面仍保留低频条件读取，以便后台稍后恢复时自动更新；ETag/304 继续复用本会话已验证响应。浏览器读回不入队、不重算。
- 健康状态下可见页面每 60 秒做轻量条件读，或被已有明确版本事件提前唤醒；报价不触发策略计算。测试需证明 304 与版本变化能正确更新状态。

新响应字段采用受版本约束的可选 delivery 元数据，现有策略/价格/收益字段保持原合同。`projection_status` 的 ready 语义不变；pending 不假装 running。工作状态不能独立授权 ready，GET 仍根据真实摘要及当前来源判断有效性。

## 9. 改动范围与交付顺序

1. 保留原六条失败原件；先修正历史依赖指纹范围及其版本，验证未来准备不使已确认历史失效、历史纠正仍能失效。
2. 增加独立工作状态、统一执行模块、分类与预算、子进程隔离及单所有者发布；CLI 与盘后改为调用统一入口。扩展部署绑定、停驻/切换/retention 对新任务的识别。
3. 有界缓存遍历及其 token/proof 回归；消费者核验仍独立，不扩大为另一套自动修数据流程。
4. 前端自动重读和具体状态说明；同步更新 `market-home-overview` canonical 与 `docs/ARCHITECTURE.md` 的 active 职责。维持一个正式实现，迁移后移除旧同步 writer 路径。
5. 在独立输出目录跑真实 120 项及故障恢复测试；按后续明确的上线目标发布/切换，再执行正式六品种恢复与 60 品种读回。此阶段不重下行情、不重跑盘后主业务、不改变账户与通知。

新工作状态为空时可从真实 last-good 和当前版本派生待办；不得清空 `.derived` 作为迁移方式。新功能停用时只停摘要执行者，保留原资产、失败证据和工作状态，GET 继续显示其真实有效性。避免同时恢复旧同步 writer 造成双写。

## 10. 验收：不以“这次能算”代替恢复验证

| 场景 | 必须证明的结果 |
| --- | --- |
| 真实 60 × 2 全入口 | 完整构建、120 项有效性、来源前后身份、输出及页面归一化通过；记录总耗时和 API 读延迟 |
| Nov6 已完成摘要构建时追加 Nov9 映射/Nov10 Session | 与当前历史读取无关的未来事实不改变当前依赖 hash，不发生全市场失效；相关未来时间真正进入消费范围时才按新范围评估 |
| 同数量历史修订、历史映射/Session/质量更正 | 仍正确失效并重算，不以减少误失效为由漏掉真实输入变化；完整周日历与 warm-up 依赖均受覆盖 |
| 已消费行与 completed 截止不变，只补齐最新候选缺失或改变相关发布状态 | 选择依赖改变必须重新评估；旧回退结果不能继续沿用旧 ready。GET 仍只读轻量描述，不读 Parquet/执行候选回放 |
| 六品种首次临时失败、其余成功 | 其余品种正常发布；只重试受影响工作；新鲜进程恢复后真实发布并自动清除当前失败 |
| 相同来源的确定性异常 | 达预算后停止计算，诊断完整；重启不重新获得无限次数；历史值保持 |
| 数据库故障超过首次三次尝试，十分钟后恢复，来源/代码均未改变 | 冷却结束和连续健康探测通过后自动开启有限新轮次，无需用户刷新或新来源；确定性错误不能借此解封 |
| 一个品种持续来源抖动或跨 job 反复失败 | 品种及全市场小时预算不被重启/改版绕过，其他品种首次构建仍有独立预算和调度资格 |
| 计算/数据库等待/缓存统计卡住 | 父级硬截止生效，其他品种继续，进程被正确回收，没有虚假 running |
| 父进程在 running、计算完成、文件替换之后分别崩溃 | 重启后核对真实文件接管，没有双 writer、重复发布或跨代覆盖 |
| 构建中来源、公式版本、权威 Session 目标变化 | 旧候选不能发布 current；最新 job 有界接续，不能通过缩窗或复用过时身份求通过 |
| D1 成功但 W1 失败 | 整品种旧完整代次保持，失败与历史截至如实可见，不拼新旧事实 |
| 网络断开后恢复、后台十分钟后恢复 | 不手动刷新即可恢复；请求不堆积，隐藏页面不轮询；没有五分钟后永久停读 |
| 401、无效 JSON、损坏缓存、304、晚到旧响应 | 不绕认证、不接纳坏值、无旧响应覆盖；缓存与传输错误相互独立 |
| 文件损坏、符号链接、容量超限、双 worker | fail-closed，无越界写、无删除 last-good、无第二 writer |
| 真实故障后的发布读回 | 精确代码身份、服务实际运行、六品种恢复和 60 品种状态逐项核对；HTTP 200 不替代语义成功 |

必须完成针对恢复并发、文件原子性及 cache token/proof 的独立 Review。稳定依赖下完整构建目标 20 分钟内，恢复后的可见页面 60 秒内自动读回；反复超限就是验收失败，不能隐藏错误或扩大预算掩盖。

本方案保证的是有界处理、故障隔离、真实历史保留、可诊断及依赖恢复后的自动接续，不声称程序缺陷、停电、网络或权威数据缺失永远不会发生。对于无法自动修复的故障，必须明确阻塞原因和真实截至，不能永久停留在一句无法追溯的通用失败提示。

## 11. 本轮设计审查

已完成独立 builder check，并修订三项重要缺口：临时故障耗尽次数后的有限恢复资格；跨 job/跨重启的持久预算与公平调度；候选选择的缺失事实及发布状态也必须进入依赖身份。复核无重要未决设计问题。该结论只针对设计，不替代实施后的并发、数据时序、缓存 proof 或现场运行验收。
